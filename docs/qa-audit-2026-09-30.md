## 附加发现（高优先级，独立于上述两项）— `test_gallery_page.py` 的 Performance 用例在"隔离运行"时**硬崩溃解释器**

这不是那个 `ratio < 3.0` 的抖动，而是**更严重**的稳定性问题，且**可在已提交代码上复现**（`test_gallery_page.py`/`gallery_page.py`/`image_loader.py` 均与 HEAD 一致）：

```
$ QT_QPA_PLATFORM=offscreen PYTHONPATH=src python -m pytest tests/test_gallery_page.py -k Performance -q
EXIT=127  bytes=0        # 进程直接死掉，0 字节输出（连 pytest 汇总都没有）

$ ... -k Performance -v -s --basetemp=... # 定位到崩溃时机
collected 14 items / 12 deselected / 2 selected
tests/test_gallery_page.py::TestGalleryPagePerformance::test_refresh_400_creates_only_first_batch   ← 打印后即崩溃
```
判别（均加 `--basetemp` 外置、`-p no:cacheprovider`）：
```
-k Pagination            → EXIT=0  5 passed
-k RefreshDeduplication  → EXIT=0  5 passed
-k Cleanup               → EXIT=0  2 passed
-k Performance           → EXIT=127 0 字节（崩溃）
-k "Performance or Pagination" → EXIT=0 7 passed   ← 有其它用例先跑就不崩
-k "Performance or Cleanup"    → EXIT=127（仍崩）
tests/test_gallery_page.py（整文件）         → EXIT=0 14 passed
tests/（全量）                                → EXIT=0 250 passed/3 skipped
```
- **症状**：仅选中/隔离 `Performance` 用例组时，进程无输出、`EXIT=127` 硬崩（`-s`+faulthandler 也拿不到 `Fatal Python error`，疑似原生级 `TerminateProcess`）；崩溃发生在第一个 perf 用例**执行中途**（用例名已打印、无结果）。
- **旁证**：本次全量套件在**并发 CPU 负载**下曾出现一次 5m17s 的挂起 + faulthandler 堆栈（同样非正常 GREEN）。孤立脚本 `qa_probe3.py` 复刻 100/800 张页面的 `refresh(force=True)` ×12 却**不崩**，故非 perf 测点本身。
- **影响**：任何"只跑一个测试文件/一类用例"的开发/CI 分工都会命中假"挂起/退出 127"，且**丢失全部输出**，极易被误当成环境噪声。

## 附加发现·深化（二次定性：Q1/Q2/Q3）

针对该硬崩做了进一步定性，**推翻了几种假设**，结论如下（所有命令均可在本机复跑）。

### 关键事实

1. **真实退出码 = `3221226505` = `0xC0000409` = `STATUS_STACK_BUFFER_OVERRUN`（即 Windows `__fastfail`）**。这解释了为什么 `-X faulthandler`、`-s`、周期性 dump **全都拿不到栈**：`__fastfail` 是 **non-continuable、绕过 SEH** 的终止，进程被直接杀掉。（`psutil` 采样得到原始码；`bash` 侧显示 `EXIT=127`／`Segmentation fault`。）
2. **不是内存/OOM**。用 `psutil` 采样子进程峰值：
   ```
   [single-400 崩溃] exit=3221226505 dur=2.9s peak_rss=76.1MB peak_wset=76.1MB out_bytes=0
   [whole module 通过] exit=0        dur=6.5s peak_rss=215.2MB peak_wset=215.2MB out_bytes=101
   ```
   **崩溃那次只用了 76MB，通过那次反倒用了 215MB** → 彻底排除 OOM / 内存峰值 / 外部强杀。
3. **确定性**（每项跑 6 次）：
   ```
   file -k Performance                 → 6/6 崩溃 (0xC0000409)
   single test_refresh_400...          → 6/6 崩溃
   single test_refresh_cost...         → 6/6 崩溃
   file -k "Performance or Pagination" → 6/6 通过
   file -k "Performance or RefreshDedup"→ 6/6 通过
   whole file                          → 6/6 通过
   ```
   崩在**第一个 perf 用例执行中途**（`-v -s` 只打印出用例名、无 `PASSED`）。
4. **不是 #12 LRU 缓存**：`il.configure_cache(max_entries=0, max_bytes=1)` 后仍 `0xC0000409`（cache_stats 显示 entries=0）。
5. **不是仓库位置/conftest/pytest.ini**：把 `test_gallery_page.py` **逐字节复制到 `%TEMP%`** 跑同样崩；`--noconftest`、外置 `--basetemp`、`-p no:cacheprovider` 均仍崩。

## 关于"已知 flaky"（`test_gallery_page.py:189 assert ratio < 3.0`）

**结论：机制确为墙钟比值（对负载敏感），但我在本机未能复现其失败；0/24 次越界。**

- 孤立复刻 `_min_refresh_ms`（12 次采样）：`min=0.82 max=1.09 mean=0.98`，**越界(≥3.0) 0/12**。
- 叠加 6 个 CPU 忙循环（重负载）：`min=0.80 max=1.60 mean=1.03`，**越界 0/12**。
- 原因：`_min_refresh_ms` 取 3 次**最小值**，且每次 `small→large` 相邻测量共享同一负载，比值被"最小化+同源负载"双重拉平，故对**均匀负载**很鲁棒；只有"恰好在 small 与 large 两次测量之间出现非对称尖峰"才会越界。
- 因此我倾向于：该断言**理论脆弱、实测稳定**，风险中低；若确需保留墙钟比值，可再加一层保护（如 `ratio < 3.0 or t_large < 250ms`）。
- ⚠️ 注意：isolated 运行时该文件还会碰到**另一个**症状——`不巧残留的 .pytest-tmp` 导致 `FileExistsError: WinError 183`（fixture setup error，非比值断言）。二者不要混为一谈。
